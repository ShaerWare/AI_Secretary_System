# PIM (ar-gs.ru): что добавить в API для работы с КП из «Секретаря24»

Для: Стаса, разработчика PIM. Документ от команды «Секретаря24», 28.10.2026.

## Коротко

«Секретарь24» (ИИ-ассистент Stalker Electric) уже работает с PIM через API-ключ «Секретарь24». Сейчас он:

- создаёт **черновик** КП через `POST /offers`, когда клиент просит КП в WhatsApp или менеджер создаёт КП в панели;
- после подтверждения менеджером или директором вызывает `POST /offers/{id}/publish` или `send-email` и отправляет клиенту ссылку;
- раз в 10 минут читает `GET /offers` и `GET /offers/{id}`, чтобы видеть статусы `sent` / `viewed` / `clarification` / `accepted`;
- по таймерам напоминает менеджеру и клиенту о КП и следит за сроком действия.

В API не хватает нескольких методов. Секретарь **уже вызывает их** по контрактам, описанным ниже. Пока PIM отвечает `404 ROUTE_NOT_FOUND`, секретарь работает в обход: делает перевыпуск вместо продления и хранит статус «проиграно» только у себя. Как только метод появится с этим контрактом, секретарь начнёт им пользоваться сам, без нашего релиза.

Поэтому важно сохранить **пути, поля и коды ошибок** из этого документа. Если удобнее сделать иначе, напишите нам, и мы поправим свою сторону.

## Что не хватает сейчас и чем это мешает

| Проблема | Что делает секретарь сейчас | Что сломано для менеджера |
|---|---|---|
| Срок КП нельзя продлить | Создаёт новое КП (новый номер), старое помечает «перевыпущено» | У клиента два номера и две ссылки, старая ссылка закрыта |
| Черновик нельзя изменить | Пересоздаёт черновик с новым номером | В PIM копятся брошенные черновики |
| Черновик нельзя удалить | Оставляет его в PIM | То же |
| Нет статусов «проиграно» / «отклонено» | Хранит у себя | В PIM такие КП выглядят «просмотренными» навсегда |
| Нет времени просмотра | Ставит время, когда *заметил* `viewed` при опросе (до 10 мин погрешности) | Таймер «открыл, но не ответил» срабатывает чуть позже |
| Нет уведомлений (webhook) | Опрашивает каждые 10 минут | Реакция на «клиент принял» — с задержкой до 10 минут |
| `GET /offers` отдаёт только 50 последних | Остальные открытые КП читает по одному | Лишние запросы к лимиту 120/мин |

## Что нужно добавить (по приоритету)

### 1. Продление и правка: `PATCH /offers/{id}`

Меняет КП **без смены номера**. Сейчас секретарь шлёт только `date_end`. Остальные поля нужны для правки черновика.

```http
PATCH /api/v1/offers/1302
Authorization: Bearer apk_…
Content-Type: application/json

{ "date_end": "2026-11-02" }
```

Поля тела (все необязательные, логика как у `POST /offers`):

| Поле | Тип | Где можно менять |
|---|---|---|
| `date_end` / `valid_days` | string `ГГГГ-ММ-ДД` или `ДД.ММ.ГГГГ` / int | в любом статусе, кроме `accepted` |
| `items` | как в `POST /offers` | только `draft` |
| `customer` / `customer_id` / `contact` | как в `POST /offers` | только `draft` |
| `request_number`, `sum_with_vat`, `cover`, `currency` | как в `POST /offers` | только `draft` |

Поведение:

- **Ссылка клиента остаётся той же.** Если `date_end` сдвинулся в будущее, а ссылка была закрыта из-за истечения срока, её нужно открыть снова (`link_active: true`). Это главное: клиент продолжает пользоваться ссылкой, которую уже получил.
- Ответ: `200` с полным объектом КП, как у `GET /offers/{id}`.
- Ошибки: `404 OFFER_NOT_FOUND`, `400 VALIDATION_ERROR` (с `field`), `409 OFFER_LOCKED`, если КП принято (`accepted`) или поле нельзя менять в текущем статусе.

### 2. Итог КП: `POST /offers/{id}/status`

```http
POST /api/v1/offers/1302/status
{ "status": "lost", "reason": "3 дня после окончания срока без ответа" }
```

- Новые статусы: `lost` (проиграно: клиент не купил) и `rejected` (отклонено до отправки: директор не согласовал).
- Принимаются также значения `accepted`, если менеджер узнал о принятии не через ссылку, и `sent`.
- `reason` — необязательная строка, показывается менеджеру в PIM.
- Ответ: `200` с полным объектом КП. Ошибки: `404 OFFER_NOT_FOUND`, `400 VALIDATION_ERROR` (неизвестный статус).
- В `GET /offers` и `GET /offers/{id}` поле `status` может принимать эти новые значения.

### 3. Удаление черновика: `DELETE /offers/{id}`

- Только для `status = draft`. Ответ: `200 {"ok": true}`.
- Если КП уже отправлялось: `409 OFFER_NOT_DRAFT`, документ остаётся.

### 4. Время событий в объекте КП

Добавить в ответы `GET /offers`, `GET /offers/{id}`, `POST /offers/{id}/publish`:

| Поле | Значение |
|---|---|
| `sent_at` | когда КП впервые отправлено или опубликовано (ISO 8601 с зоной) |
| `viewed_at` | первый просмотр клиентом |
| `last_viewed_at` | последний просмотр |
| `views_count` | сколько раз открывали |
| `accepted_at` | когда принято |
| `status_changed_at` | последняя смена статуса |
| `clarification_text` | что клиент спросил, если статус `clarification` (если вопрос задаётся через страницу КП) |

Секретарь уже читает `viewed_at` из уведомлений (п. 5). Остальные поля он начнёт использовать, когда они появятся.

### 5. Уведомления (webhook)

PIM сам сообщает секретарю об изменении КП, и опрос раз в 10 минут становится запасным вариантом.

- **Адрес:** `POST https://ai-sekretar24.ru/webhooks/pim`. Удобно сделать его настраиваемым в PIM: Настройки → API, рядом с ключом.
- **Заголовок:** `X-Webhook-Secret: <секрет>`. Секрет выдаём мы, он же задаётся в PIM. Без верного секрета секретарь отвечает `401`.
- **Тело:**

```json
{
  "event": "offer.viewed",
  "occurred_at": "2026-10-28T09:15:00Z",
  "offer": { "...": "полный объект, как в GET /offers/{id}" }
}
```

- **События:** `offer.sent`, `offer.viewed`, `offer.clarification`, `offer.accepted`, `offer.updated` (после `PATCH`), `offer.status_changed`, `offer.expired` (срок вышел, ссылка закрыта).
- **Повторы:** при ответе не `2xx` повторить 3–5 раз с нарастающей паузой. Секретарь обрабатывает событие идемпотентно (сверяет с `offer`), поэтому повтор безопасен.
- Если `offer.viewed` приходит на каждый просмотр — это тоже нормально.

### 6. Фильтры в `GET /offers`

- `status=sent,viewed` — несколько статусов через запятую.
- `updated_since=2026-10-28T00:00:00Z` — только изменённые после момента.
- `offset` (или `page`) — постраничная выборка, сейчас доступны только 50 последних.

### 7. Варианты срока действия (по желанию)

Директор решил, что КП действует **1–3 дня**. В секретаре варианты срока настраиваются (сейчас 1, 2 и 3 дня, по умолчанию 3). Если в PIM будет такой же список в настройках КП, его стоит отдать в API, чтобы оба места предлагали одно и то же:

```http
GET /api/v1/settings/offers
→ { "validity_presets": [1, 2, 3], "default_valid_days": 3 }
```

## Как секретарь понимает `date_end`

Секретарь отправляет `date_end` как **последний день действия включительно** по времени Казахстана (UTC+5). Например, КП «на 1 день», созданное 28.10, действует до 29.10 включительно. Если в PIM `date_end` означает другое (например, «до начала этого дня»), сообщите нам, и мы сдвинем дату на своей стороне.

## Как проверить

1. Добавьте метод по контракту.
2. На тестовом КП (черновике) вызовите его тем же ключом, например:
   `curl -X PATCH -H "Authorization: Bearer apk_…" -H "Content-Type: application/json" -d '{"date_end":"2026-11-02"}' https://ar-gs.ru/api/v1/offers/<id>`
3. Напишите нам. Секретарь начнёт пользоваться методом сразу, но мы проверим кнопки «Перевыпустить» и «Проиграно» в панели и отпишемся.

Если что-то из этого в PIM уже есть, но под другим путём или названием, пришлите описание. Обновлённый `GET /api/v1/openapi.json` тоже подойдёт.
