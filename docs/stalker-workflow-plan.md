# План работ: MASTER WORKFLOW Stalker Electric v1.2 → код

Составлен 2026-09-01 по итогам сверки документа v1.2 (10.08.2026) с текущим кодом
репозитория. Ссылки вида `§N` — на пункты MASTER WORKFLOW.

Принцип разбивки: каждая фаза даёт самостоятельно проверяемый результат и не
оставляет «доделать позже, чтобы заработало». Фазы 0–4 можно вести параллельно
разными людьми; фаза 5 — фундамент, после которого 6–10 идут почти линейно.

Оценки — ориентир для одного разработчика, в днях чистой работы.

## Фаза 1. `OUTBOUND_APPROVAL` и канал директора ← начинать с неё

**Зачем первой (поднято с 3-го места §57):** сейчас боты отвечают клиенту сразу и
напрямую. Пока шлюза нет, любой включённый канал уже нарушает TEST_MODE, и
выпускать агента на живой поток нельзя. Всё остальное строится поверх.

### 1.1. Единый исходящий шлюз (2 дня)

Новый модуль `modules/director/`:

```
outbound.py   send_or_queue(channel, target, text, *, meta, bypass=False)
models.py     OutboundMessage: id, channel, target, text, status, deal_id,
              session_id, created, decided_by, decided_at, edited_text, error
config        OUTBOUND_APPROVAL: DIRECTOR_ALWAYS | AUTO_IF_NO_FLAGS
              DIRECTOR_TELEGRAM_USER_ID
```

Один параметр в `ConfigService` (переключается из админки, не из `.env` — чтобы
снять TEST_MODE без деплоя). Логика подтверждения живёт **только здесь**, по
сценариям не размазывается — прямое требование §1.2.

Все каналы переводятся на шлюз: `whatsapp_bot/handlers`,
`modules/channels/widget/router_public.py`, `telegram_bot/services/llm_router.py`,
mobile. Ни один канал не пишет клиенту напрямую.

### 1.2. Бот директора в Telegram (2 дня)

- Команды только от привязанного `telegram_user_id` (§1.3), остальные аккаунты игнорируются.
- Карточка подтверждения: готовый текст + инлайн-кнопки **Отправить / Изменить / Отменить** (§6.4 — одно касание, не вопрос «что будем делать?»).
- «Изменить» → директор присылает свой текст → уходит он.
- Формат уведомления §45 — переиспользуемый рендерер `director/notify.py`, им же пользуются все следующие фазы.

### 1.3. Автоответ о приёме (0.5 дня)

Фиксированный шаблон §2.5 — единственное, что уходит с `bypass=True`. Без цен,
товаров, сроков и обязательств.

**Готово, когда:** сообщение клиента в WhatsApp → клиенту мгновенно уходит только
автоответ; ответ ассистента лежит в очереди; директор жмёт «Отправить» в Telegram
— уходит клиенту; переключение флага в `AUTO_IF_NO_FLAGS` отправляет без очереди.

**Итого: ~4.5 дня.**

## Фаза 2. Классификация входящих и заглушки веток

**Зачем:** приоритет 1 из §57 — заявки на ДГУ, ремонт и шкафы перестанут теряться
сразу, без остальной машины.

### 2.1. Классификатор (3 дня)

Новый модуль `modules/inbox/`:

- `models.py` — `InboundMessage`: канал, отправитель, телефон/email, текст, вложения, `class_l1`, `class_l2`, `confidence`, `deal_id`.
- `classifier.py` — правила (регэкспы на DPD-трек, прайс-лист, платёжку, тендер) + LLM-фолбэк для неоднозначного; уровень 1 (§2.3) и уровень 2 для `REAL_REQUEST` (§2.4).
- `UNKNOWN` и низкая уверенность → директору, не удалять (§2.7).

### 2.2. Спам-карантин (1 день)

Пометка `SPAM`, вывод из рабочей очереди, хранение 30 дней, еженедельный дайджест
директору (§2.6). Задача `spam-digest` в `TaskRegistry`. Удаление спама запрещено
(§44.16).

### 2.3. Ветки-заглушки 4B (2 дня)

`DGU_SERVICE`, `ELECTRONICS`, `COMMISSIONING`: фиксированный набор вопросов одним
сообщением (§4B.1–4B.3), сбор ответов и вложений, карточка директору. Прайсовый
поиск не запускается.

### 2.4. PANEL_VERBAL (1 день)

5 вопросов одним сообщением (§4A.3), карточка формата §4A.4 с явным списком «не
ответил». Бот не считает шкаф и не называет цену.

### 2.5. Спец-типы входящих (2 дня)

- `DPD_TRACK` (§2.8): распознать трек, найти сделку, привязать, новую не создавать.
- `PRICE_LIST_UPDATE` (§2.9): распознать поставщика и файл, спросить директора, после подтверждения перезаписать прайс и зафиксировать дату.
- `EXISTING_DEAL_MESSAGE` (§2.10) и дополнение к заявке до/после КП (§2.11).

**Готово, когда:** на выборке из «Неразобранного» amoCRM классификатор даёт отчёт
по типам; заявка на ДГУ порождает карточку директору, а не поиск по прайсу.

**Итого: ~9 дней.**

## Правила работы по этому плану

- Ветки: `local/feat/stalker-<фаза>-<кратко>`, PR в `main`; прямой пуш в `main` запрещён.
- Каждая фаза заканчивается прогоном `ruff check .` и `pytest tests/ -m "not integration"`.
- Новые Python-зависимости ставятся в прод-venv руками — `deploy.sh` их не подхватывает.
- Правки поиска и цен в живых каналах требуют `systemctl restart ai-secretary` — код кэшируется в процессе.
