## Unified product search (`modules/procurement/`)

Code-pipeline «единый поиск позиции» для торгового ассистента (StalkerElectric). Модель `ProductOffer` (table `product_offers`) — единое структурное представление оффера из любого источника: `source` (`site`/`ekf`/`supplier`), `article`, `name`, `price`, `in_stock`, `lead_time_days`, `url` + `UniqueConstraint(source, source_key)` для upsert. `OfferService.replace_source_offers()` делает полный ре-синк одного источника (схлопывает дубли `source_key` внутри одной выборки — пагинация WooCommerce сдвигается, если каталог меняется на ходу, и товар попадает на две страницы; раньше весь синк падал на `UNIQUE(source, source_key)` и сутки оставались без обновления); `OfferService.search()` детерминированно ранжирует (порядок ранга ниже) и **возвращает `[]`, если ничего не найдено — не выдумывает позиций** (жёсткое требование клиента реализовано архитектурно, а не промптом). `OfferService.search()` **сворачивает омоглифы** (`_fold` — визуально неотличимые кириллические буквы в латиницу, только для сопоставления: каталог расколот почти пополам, 11 501 позиция с кириллической А/Р/В после цифры против 10 167 с латинской, и запрос «АВР 630А» видел лишь свою половину — «ввод резерва АВР NXZM-630S/3B 3P 630A» с латинской A выпадал из выдачи целиком при 36 штуках на складе; буквы б/г/з в таблицу НЕ входят, «б» это не «6»; сворачивать токены надо ПОСЛЕ стоп-слов и синонимов, иначе свёрнутое слово в `_STOPWORDS` не найдётся), фильтрует стоп-слова (мета-запросы «запрос/стоимость/счёт», «из наличия/помоги/найти/подобрать», единицы «квт/вт/ква» и «ампер» — на «нужен АВР 630 ампер» выдача состояла из АМПЕРМЕТРОВ, потому что «ампер» был единственным значимым токеном и попадал в «амперметр», а «авр» и «630» коротки и значимыми не считаются), делает префикс-стемминг (`_stem` — 70 % длины слова, но не короче 6: контактор→контакт, электродвигатель→электродвига; плоские 6 символов превращали «электродвигатель» в «электр» и тянули в выдачу всю электроустановочную продукцию) + расширяет аббревиатуры (`_SYNONYMS`: ЧРП/ПЧ/частотник→преобразователь частоты; УЗО/УПП/дифавтомат). **Порядок ранга**: article_exact → article_partial → не-аксессуар (`_is_accessory_for_query` — «Катушка управления ДЛЯ КОНТАКТОРА» ниже контакторов, но не когда просят саму катушку) → lead-токен (название начинается с первого значимого слова запроса: сам товар выше того, что его лишь упоминает) → **близость номинального тока** (`_amperage`/`_amp_bucket`: «18А»/«120A», но не «NC1-1810» и не «220В»; на запрос «20А 2НО» позиция на 225 А с 2НО не должна обгонять 18-амперную с 1НО+1НЗ — для электротехники номинал определяющий; позиция без указанного тока идёт ниже подходящих, но выше явно чужих; если ток не назван в запросе — измерение нейтрально) → совпадения по целому слову (`strong` — «Контактный зажим» за 293 ₸ не обгоняет «Контактор» за 6 237 ₸) → число совпавших токенов → head-match. **Тай-брейк**: in_stock → **есть ли цена вообще** (треть site-каталога синкается с `price=0`, и при сортировке по возрастанию цены эти строки вытесняли реальные позиции из выдачи) → `SOURCE_PRIORITY` site<ekf<supplier → price. Строка, совпавшая только по случайному числу («100» из «ТТИ-А 100/5» → «упаковка 100 шт.»), кандидатом не считается — но только если в запросе вообще есть слова длиннее 3 символов (иначе ломались бы артикульные запросы вида `NXC 18`). Матчит name+category; возвращает `confident` (артикул или ≥2 значимых токена) — триаж по нему отсекает спам-темы писем. Регресс-тесты ранжирования: `tests/unit/test_offer_search_ranking.py`. ВАЖНО: правки search в live-каналах требуют рестарта (код кэшируется в памяти процесса). Ранжирование идёт по лёгким Core-кортежам (id/source/article/name/category/price/in_stock), полные строки достаются второй фазой только для победителей — полная ORM-выборка 57 тыс. офферов стоила ~1,5 с на каждое сообщение чата. **YML-фид наличия** (`modules/procurement/feed_adapter.py`, env `PROCUREMENT_FEED_URL`, задача `procurement-feed-sync` в 23:40 UTC — строго между каталогом 23:30 и поставщиками 23:50): сторона клиента отдаёт фид в формате Яндекс.Маркета (`vendorCode`/`price`/`count`/param «Срок поставки»), перечисляющий ТОЛЬКО доступное к заказу — 2 299 позиций, у всех `available="true"` и `count >= 1`. Это тот источник наличия, которого каталогу не хватало (WooCommerce учёт не ведёт). **Фид не отдельный каталог, а слой поверх site-офферов**: `vendorCode` совпал с `sku` сайта у 2 293 из 2 299, цена — у всех 2 293 до тенге, противоречий по наличию ни одного, а у 964 позиций наличие было неизвестно и фид его подтверждает. Поэтому `OfferService.apply_feed_stock()` обновляет `in_stock`/`stock_qty`/`lead_time_days` существующих строк по индексированной колонке `article` (отдельный `source` дал бы по два почти одинаковых оффера на товар и съел бы окно выдачи из 8 позиций); артикулы, которых в каталоге нет (6 штук) — свои строки `source='feed'`, видимые клиенту наравне с сайтом (`_inject_offer_context` пускает клиентским каналам `{site, feed}`, дилерские строки поставщиков по-прежнему только менеджеру). Срок берётся по ВЕРХНЕЙ границе диапазона («1-3» → 3 дн.). Пометка прогона лежит в `extra.feed_stock` и снимается в начале следующего: раскупленная позиция, выпавшая из свежего фида, иначе навсегда обещала бы склад (§5.5). Порядок задач обязателен — синк каталога перезаписывает строки сайта целиком, так что фид идёт ПОСЛЕ него; упавший прогон фида оставляет «наличие уточняется», то есть ошибается в безопасную сторону. Параллельно пишется RAG-коллекция `stalker-stock` («Stalker Electric — наличие (фид)», 30 md-документов по категориям + сводка, `data/stalker-feed-dataset/`) через событие `DatasetSynced` — её привязывают к stalker-сессиям вместе с коллекцией каталога id=6. Описаний и характеристик в фиде пока нет (разработчик клиента их не отдаёт), поэтому семантический слой по-прежнему держится на выгрузке WooCommerce. Ручной прогон: `POST /admin/procurement/sync-feed`. Адаптеры населяют общую таблицу: `site_adapter.sync_site_offers()` (WooCommerce→офферы, 30 163; `_availability()` читает ПЕР-ПОСТАВЩИКОВЫЕ меты товара — поле на склад плюс срок рядом: `EKF_Stock_0`+`EKF_Stock_0_delivery` («1-2 дня», в сводке он подписан SUNWELL — тот же партнёр), `Chint_Stock_0`+«3-4 дня», `Axima_Stock_0`/`Axima_Stock_2`+«1 день»; остаток приходит строкой с целым, срок — строкой, из которой берётся ВЕРХНЯЯ граница. Сводку `_remote_stock_blocks` читать НЕЛЬЗЯ: после смены темы (28.09.2026) она разъехалась с исходными полями и врёт в обе стороны — срок в ней прибит константой `1-2 дн.` для КАЖДОГО поставщика (у Chint собственное поле говорит «3-4 дня», так в 39 случаях из 40), а количество расходится в 67 случаях из 77, вплоть до «AXIMA 28 шт.» там, где оба склада Аксимы дают ноль. Сводке оставлен один поставщик — ПРОМСИТЕХ, у которого своих полей нет, и срок оттуда не берётся никогда. Когда позиция есть у нескольких, берём САМОГО БЫСТРОГО из имеющих её в наличии и показываем его остаток с его же сроком: суммировать склады разных поставщиков нельзя, «12 шт. за 2 дня» означало бы, что приедут и те семь, что лежат у четырёхдневного. Все известные поставщики по нулям → `None` («уточняется»), а не `False`: позицию может возить тот, чьих полей на сайте нет. Живая выборка 1200 товаров: 51 с подтверждённым наличием, сроки 4 дн. (31) / 2 дн. (16) / 1 день (4) — по старой логике все получили бы «2 дн.». Меты видны только через authenticated v3, публичный Store API их НЕ отдаёт; HTML сайта с 28.09.2026 закрыт антибот-заглушкой «Проверка безопасности», так что разбор страниц как запасной путь недоступен. Собственный учёт WooCommerce бесполезен и наличием НЕ считается: `manage_stock` выключен у всех товаров, `stock_status=instock` у всех 30 163, `outofstock`/`onbackorder` — ноль; прежнее `in_stock=True` заставляло ассистента писать «✅ В наличии» про любую позицию каталога, что прямо запрещено §5.5/§44.12 MASTER WORKFLOW) + `suppliers/` (config-driven парсер, 7 поставщиков). **`modules/procurement/suppliers/`**: `registry.py` (per-supplier конфиги по реестру клиента Reestr v3 лист5 — format/header_row/cols/currency/markup_pct/stock_file; форматы: `xlsx`/`xls`(xlrd,1С)/`pdf_lines`/`pdf_table`), `parser.py` (openpyxl+xlrd+pdfplumber; `parse_number`; мерж остатков; трекинг категорий 1С), `adapter.py` (`sync_supplier`/`sync_all_suppliers` → `replace_source_offers(..., scope_key=cfg["key"])` — удаление по префиксу `{key}#%`, устойчиво к переименованию). **«Остаток не указан» ≠ «нет в наличии»**: парсер ставит ключ `stock` только когда остаток реально прочитан, адаптер пишет `in_stock=None` при неизвестном и `False` только при явном нуле. Файлы остатков перечисляют ЛИШЬ то, что есть (у SunWell/EKF 838 артикулов против 20 728 строк прайса; у Аксимы/Chint пустые ячейки без единого явного нуля), и прежнее `(row.get("stock") or 0) > 0` помечало 20 738 строк как «НЕТ в наличии» без оснований — зеркальное нарушение того же §5.5. Колонки xlsx/xls можно искать по заголовкам (`header_labels` → `parser.resolve_columns`, поиск со строки с «Артикул», `stock` собирает ВСЕ складские столбцы и суммирует): октябрьская выгрузка Аксимы сдвинула всё на столбец и добавила склад «Рыскулова». Поставщики (наценка per-supplier из реестра): promsitech (`Остатки от*.xls`, цена как есть, `purchase_hidden` — закупка не раскрывается, флаг нулевой маржи не ставится), sunwell ×1.30, aksima ×1.30/max-РРЦ, aksima_chint_rrc (РРЦ), xtrade ×1.40, elektrokomplekt/ЭКТ ×1.25, megazakaz (USD, ×1.20×1.16). Прайсы из env `SUPPLIER_PRICES_DIR`; файлы прайсов НЕ в git (`docs/файлысталкера/` в .gitignore — дилерские цены). На проде каталог постоянный и **вне репозитория** — `/var/lib/ai-secretary/supplier-prices` (прежний `/tmp/stalker_prices` слетал при ребуте, а внутри репо его снёс бы `git clean`). Файлов нет — `sync_all_suppliers` логирует FileNotFoundError по каждому поставщику и не роняет остальных. **Чат-интеграция** (`modules/chat/facade.py`): `_inject_offer_context` для procurement-сессий (коллекция в env `PROCUREMENT_CATALOG_COLLECTIONS`, default {6}). Поисковый запрос строится **из диалога**, а не из последней реплики (`modules/procurement/query_builder.py`): один дешёвый LLM-вызов на последних 6 репликах возвращает `{query, exclude}`. Без этого уточнение «модульный не подходит, нужен промышленный» искалось по слову «модульный» — то есть по тому, что клиент только что отверг, — и ассистент отвечал «в каталоге только модульные», хотя силовых контакторов на сайте 556. Первое сообщение сессии вызов пропускает (сырой текст и есть запрос); любой сбой LLM/парсинга — фолбэк на сырой текст, чат не ломается. **Слова, которые ввёл в оборот сам ассистент, из запроса вычищаются кодом** (`_drop_words_only_the_assistant_used`), а не только запрещаются промптом: клиент спросил «АВР есть на 630А?», ассистент предложил «Устройство АВР ТСР1/ТСM … EKF PROxima», клиент ответил «мне нужен из наличия» — и билдер собрал `устройство АВР 630А 3Р EKF PROxima`, подставив бренд и слово «устройство» из ответа САМОГО ассистента. Поиск вернул только EKF, три позиции «Устройство АВР …» забрали всё окно выдачи, и Chint NXZM-630S/3B 630A (36 шт. на складе) до клиента не доехал — воронка: что ассистент показал первым, то и становилось требованием навсегда. Критерий именно «сказал ассистент, но не клиент», а не «нет у клиента»: нормализацию модель делает своими словами («нужен промышленный» → «контактор силовой»), и «силовой» не произносил никто — такие слова нужны. Числовые номиналы («630а», «3р», «220в») не отбираются никогда, даже от ассистента: он мог уточнить «трёхполюсный?» — «да». `exclude` вычитается из выдачи в `OfferService.search`. `OfferService._attach_supply()` дополняет позиции сайта тем, что известно о них у поставщиков (18 015 из 30 163 артикулов каталога есть в прайсах): в `offer["supply"]` идут `available`/`supplier_name`/`qty`/`as_of`, и `facade._supply_label()` превращает это в «есть у поставщика — уточнить только СРОК» (клиенту без имени поставщика, менеджеру с именем, остатком и датой прайса). Поиск по индексированной колонке `article` вариантами регистра, не `upper(trim(...))` — иначе каждое сообщение чата сканирует прайсы целиком. Инъектит ТОЧНЫЙ keyword-поиск офферов (цены/артикулы/КП — принцип клиента: КП только точное) + SUPPLEMENTARY семантику каталога через `wiki_rag.retrieve_async(collection_id=6)` (богатые описания/смысл для вагих запросов типа «чем питать насос»→ПЧ; голые офферы НЕ индексируем в вектор — замер 2.8ч+шум); ГЕЙТ видимости — `session.source=='admin'` видит supplier-дилерские цены, клиентские каналы (widget/telegram/mobile) только site-розницу. **Остатки из прайсов идут и клиенту, но называются иначе.** 02.10.2026 по блокам питания DR-*-24 сайт остатка не подтверждал, а прайс SunWell/EKF показывал 34 шт., ассистент выдал «✅ В наличии», и заказчик ответил «их же нет в наличии». Сначала источник отключили для клиентских каналов (`with_supply=manager_ctx`), но 03.10.2026 директор подтвердил, что файлы актуальны, и попросил вернуть — «есть у поставщика, срок уточняется» это ровно то, что он просил показывать с самого начала. Вывод: **разводить склад и прайс надо СЛОВАМИ, а не отключением источника**. Поэтому клиентский ярлык звучит «есть у поставщика (не на нашем складе) — уточнить только срок поставки», а ✅ и слово «в наличии» разрешены ТОЛЬКО для пометки «в наличии N шт.» (подтверждённый остаток сайта). `with_supply=False` остался для мест, где прайс не к месту (КП, триаж писем). Имя поставщика и закупочная цена по-прежнему только менеджеру. В ярлыке для менеджера дата пишется как «прайс, загружен DATE», а не «прайс от DATE»: `supply.as_of` это `ProductOffer.updated`, то есть когда МЫ разобрали файл, а не дата самого файла («ОСТАТКИ 14.07» могли перечитать сегодня). Провайдер `claude_bridge` без tools → поиск = код-шаг. Роутер `/admin/procurement/{status,search,sync,sync-suppliers,price,kp,route}` (RBAC `sales`). **Маршрутизация** (`routing.py`, Reestr лист3): `SUPPLIER_META` (7 поставщиков вкл. promsitech/eltech без файлов, типы A/B/C), `CATEGORIES` (14 категорий keyword→упорядоченные поставщики), `classify`/`route(query,city)` (Атырау→ЭКТ первым, ELTECH competitor). Эндпоинт `GET /admin/procurement/route`; чат «не найдено» (менеджер) подсказывает у кого запросить. **amoCRM-триаж** (`modules/crm/triage.py` + `GET /admin/crm/triage`): неразобранные лиды (`get_unsorted_leads`, добавляет `_body`=`metadata.content_summary` для mail) → матчинг/КП по ТЕМЕ (точно, confident по значимым токенам ≥4 — спам не проходит), маршрутизация по тема+тело (recall), `body_preview` для менеджера → {routing, matches[client_price], suggestion}; ловит мёртвый токен → `{ok:false, reason:reauth_needed}` (`GET /admin/crm/auth-url`). Дальше: тело чатов (get_chat_history) + LLM-извлечение позиций из длинного письма. Задачи `procurement-site-sync` (daily 23:30 UTC) и `procurement-supplier-sync` (daily 23:50 UTC — после каталога: оба источника пишут в одну таблицу). Без второй прайсы разбирались только руками через `POST /admin/procurement/sync-suppliers`, и положенный в папку свежий файл никто не подхватывал — офферы поставщиков простояли нетронутыми с 24.07 по 28.09.2026. **Генерация КП** (`kp.py`): `build_kp`/`build_kp_for_queries` — спецификация из priced-офферов → markdown (позиции, Итого без НДС/НДС 16%/с НДС, курс+дата если USD, строка доставки по факту веса, срок действия; поставщиков клиенту НЕ раскрывает, Мегазаказ как бренд Stalker, zero-margin/нерасчитанные → flags не в итог; черновик на директора).
