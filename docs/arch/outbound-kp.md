# Outbound approval queue and КП workflow

> Part of the project map in [CLAUDE.md](../../CLAUDE.md). Split out of CLAUDE.md verbatim on 2026-10-31; update it in the same PR as the code it describes.

**Outbound approval queue + channel monitoring** (`modules/outbound/`, CRM page tabs «Подтверждение» / «Мониторинг»): the single place deciding whether an assistant reply goes straight to the client (MASTER WORKFLOW §1.2). Mode is per channel instance, stored in `system_config` key `outbound_approval` (`{"instances": {"whatsapp:<id>": {"mode": "auto"|"approval", "ack_text"}}, "unanswered_minutes", "pending_alert_minutes"}`), switched live from the admin panel — no bot restart. Default `auto` = old behaviour. Flow: the WhatsApp bot gets the LLM reply, then `whatsapp_bot/services/outbound.submit_reply()` → `POST /admin/outbound/submit`; `approval` → row in `outbound_messages` (`draft_text` immutable, `text` editable) and the client gets only the fixed acknowledgement (§2.5, once per 30 min per target). Approve (`POST /admin/outbound/messages/{id}/approve`, optional edited `text`) is sent by the **orchestrator** via `modules/outbound/sender.py`, which builds a Bridge/Cloud client from the instance row; status goes through a `sending` claim so a double click can't send twice; failure → `failed` with error, retryable. Edit/reject rewrite the assistant's `chat_messages` row so the dialogue history equals what the client actually saw. In approval mode `modules/chat/router.py` skips the amoCRM turn note (it only has the draft) — the queue files it with the sent text. If the submit call itself fails, the bot uses the last mode it saw (`approval` → drops instead of sending). `GET /admin/outbound/monitor`: bot process, bridge link state, last inbound/outbound per channel, **unanswered dialogues** (last active message is the client's, older than the threshold — catches dead bots/401s that a "connected" bridge hides), queue age, failed sends, amoCRM link. Only WhatsApp goes through the queue; Telegram/widget are monitored only.

**КП: черновик в PIM → подтверждение → таймеры** (`modules/kp/`, CRM page tab «КП»): the КП document itself lives in the client's PIM ar-gs.ru (`modules/kp/pim_client.py`, env `ARGS_PIM_URL`/`ARGS_PIM_API_KEY`, spec at `{ARGS_PIM_URL}/openapi.json`); the secretary keeps a mirror (`kp_quotes`, `kp_timer_rules`, `kp_events` — created by `create_all`, no migration) for approval, delivery and timers. **The assistant only ever creates drafts** (`POST /offers` is always a draft): in a procurement WhatsApp session (`source=whatsapp` and the session/instance **explicitly** attaches a procurement catalog collection — `facade._is_procurement_session`, `rag_mode="all"` never counts) a client message matching `extract.KP_REQUEST_RE` («пришлите КП», «выставьте счёт») fires `kp_service.maybe_auto_draft` from `modules/chat/router.py` (`_maybe_draft_kp`, fire-and-forget, one draft per session per 30 min, setting `system_config.kp_settings.auto_draft`, default on, checkbox in the settings of the CRM «КП» tab / `PUT /admin/kp/settings`; nothing happens while `ARGS_PIM_API_KEY` is empty): one LLM call lists positions+qty from the dialogue, each is matched by `offer_service.search(..., with_supply=False)` and goes into the КП only if the match is `confident` and priced — everything else lands in `flags` for the manager, never in the document (the PIM's own rule for AI agents: never invent goods or prices). An article the PIM catalog doesn't know (`PRODUCT_NOT_FOUND`) is re-sent as an own position with the article in the name. **WhatsApp КП ride the existing outbound queue**: the draft enqueues an `outbound_messages` row (`outbound_service.enqueue` — queued regardless of the channel's auto/approval mode) whose text keeps a `{link}` placeholder; approving it on «Подтверждение» or on «КП» is the same call — `outbound_service.approve` asks `kp_service.find_by_outbound`/`before_outbound_send`, which refuses expired/closed quotes, calls PIM `publish` and fills in the client link at that moment; `after_outbound_send` marks the quote `sent` and appends the sent text to the chat so the assistant knows. The link between a queue row and a КП is kept on the КП side (`kp_quotes.outbound_message_id`, `kp_events.dedup_key = "outbound:<id>"` for timer reminders) — `outbound_messages` has no КП columns; a failed КП lookup never blocks an ordinary reply, but a text still holding `{link}` is never sent. Email (`send-email`) and link-only (`publish`, manager sends) deliveries are approved on the КП tab or from the messenger card. Task `kp-timers` (every 10 min): `sync_from_pim` (latest 50 via `GET /offers` + open ones one by one; imports offers made by hand in the PIM within 30 days as `origin=pim`; a draft that the PIM reports `sent` cancels our queued copy so it can't go out twice), then `run_timers`: anything past validity → `expired` (pending queue copies cancelled), then rules from `kp_timer_rules` (CRUD on the tab; triggers `not_approved`/`not_viewed`/`viewed_no_reply`/`before_expiry`/`expired` + `offset_hours`; actions `notify` (panel «Требуют внимания» + Telegram via `KP_TELEGRAM_*`→`LEAD_TELEGRAM_*` + WhatsApp to staff numbers `kp_settings.notify_whatsapp_numbers` from `notify_whatsapp_instance_id`→`followup_instance_id`, sent directly via `outbound/sender.send_whatsapp` — internal pings, not client messages, so no approval queue; the same `_notify` fires on an assistant-made draft and on «клиент принял КП»), `client_message` (always queued for approval, max one per 6 h per quote), `mark_lost`), each fires once per rule+`valid_until` (`timers.dedup_key`), expiry rules ignore offers imported already expired. Validity is a calendar date in UTC+5 (`timers.valid_until_for`: N days = today+N, inclusive); presets/default in `system_config.kp_settings` (director 28.10.2026: 1/2/3 days, default 3). An expired offer is never prolonged silently: «Перевыпустить» tries `PATCH /offers/{id}` and, while the PIM answers `ROUTE_NOT_FOUND` (`PimNotSupported`), creates a new draft (new number) and marks the old one `superseded`; `lost` goes to `POST /offers/{id}/status` the same way. Those missing PIM methods + webhook `POST /webhooks/pim` (`X-Webhook-Secret` = `ARGS_PIM_WEBHOOK_SECRET`) are specified for the PIM developer in `docs/pim-api-for-kp.md` — the secretary already calls them by that contract, so they start working without a release. Tests: `tests/unit/test_kp_timers.py`, `tests/unit/test_kp_workflow.py`.

**КП in the managers' messengers** (`modules/kp/messenger.py`): the draft notification is the КП itself — «Что просит клиент» (`summary` from the same extraction LLM call, kept as a `kp_events` info row prefixed `Запрос клиента: `), «Что подобрал ассистент» (positions with the client's own wording `items[].query`, carried over by position when the PIM's items replace ours), «⚠ Не вошло в КП» (`flags`) and the client text (`{link}` shown as `[ссылка на КП]`, turned back on edit). While the quote is `pending`/`failed` the card — and timer pings about it — carry actions, all of them the same `kp_service.approve` / `update_quote(message)` / `reject` the panel calls, so a human still approves every send. **Telegram**: inline buttons `kp:approve|edit|reject:<id>`; «Изменить текст» sends a force-reply prompt ending `КП #<id>`, the reply replaces the text and a fresh card comes back; plain «ок 18» works too; only updates from the notification chat count. The notification token on prod is `@ai_sekretar24bot`, which is also a running bot instance — two pollers of one token 409 each other, so that bot's process receives the presses (`telegram_bot/handlers/kp.py`, first router; non-commands `SkipHandler` on to the chat) and forwards them to `POST /admin/kp/telegram-update`; the `kp-telegram` task long-polls only a dedicated token no enabled `bot_instances` row owns. **WhatsApp**: the bot asks `POST /admin/kp/staff-message` for every incoming text before the assistant (`whatsapp_bot/services/staff.py`); a sender in `notify_whatsapp_numbers` is never passed to the assistant — commands «ок 18», «текст 18: …» (saves, does not send), «отмена 18», «кп» (list), anything else gets the help + pending list. The handle «18» is the КП number's digits without leading zeros; without a number the command applies only when exactly one draft is pending. Both bot endpoints accept only the internal bot sessions (`__internal_bot__`, `__internal_wa_bot__`). Tests: `tests/unit/test_kp_workflow.py` (messenger section).
